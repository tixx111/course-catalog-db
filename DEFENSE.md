### 3. Демонстрация работы индекса на 50 000 строк (база `idx_demo`)
Переключитесь на демонстрационную базу:
```sql
\c idx_demo
```

Покажите разницу в скорости с индексом:
```sql
EXPLAIN ANALYZE SELECT * FROM enrollments WHERE student_id = 777;
```
*Что сказать:*
> «В таблице `enrollments` 50 000 строк. Благодаря B-tree индексу `enrollments_student_id_idx` база использует `Bitmap Index Scan` и находит 3 нужные строчки за **0.007 миллисекунды**. Если бы индекса не было, PostgreSQL делал бы `Seq Scan`, читая все 50 000 строк подряд и тратя на это около 5 миллисекунд (в 700 раз дольше)».

Также можно показать, почему на маленькой таблице `courses` индекс не используется:
```sql
\c course_catalog
EXPLAIN SELECT * FROM courses WHERE id = 'api-design';
```
*Что сказать:*
> «Здесь оптимизатор выбрал `Seq Scan` вместо индекса первичного ключа, потому что в таблице всего 6 строк — они умещаются в один 8-килобайтный блок диска, и прочитать его напрямую быстрее, чем сначала лезть в индекс».

## ЧАСТЬ 2. Ответы на теоретические вопросы

### 1. Архитектура и дизайн схемы
* **Зачем 3 таблицы, а не одна большая (плоская)?**
  * *Простыми словами:* В плоской таблице возникают 3 аномалии:
    1. *Обновления:* переименовал курс в одной строке — в остальных старое название (рассинхрон).
    2. *Удаления:* удалил последнего записанного студента — стёрлись данные о самом курсе.
    3. *Вставки:* нельзя создать новый курс без студентов (придётся писать `NULL` в поля студента).
  * *По-научному:* Схема приведена к 3-й нормальной форме (3NF), устраняя транзитивные зависимости и дублирование данных.
* **Почему `courses.id` — текст (slug), а `students.id` — число?**
  * *Курс:* Слаг (`modern-frontend`) формирует чистые, понятные REST API URL (`/courses/modern-frontend`) без лишних запросов.
  * *Студент:* Имя и почта человека могут измениться. Суррогатный числовой ключ (`bigint GENERATED ALWAYS AS IDENTITY`) компактен (8 байт), неизменяем и быстрее всего работает во внешних ключах.
* **Почему на курс `ON DELETE RESTRICT`, а на студента `ON DELETE CASCADE`?**
  * *Курс (`RESTRICT`):* Нельзя случайно удалить курс из каталога, пока на него записаны люди, иначе сотрётся учебная история.
  * *Студент (`CASCADE`):* Если удаляется профиль студента, все его персональные записи на курсы должны удалиться автоматически («паровозиком»).
* **Зачем `timestamptz`, а не `timestamp`?**
  * `timestamptz` хранит абсолютный момент времени в UTC. Обычный `timestamp` не хранит часовой пояс, из-за чего при смене таймзоны на сервере время «поплывёт».
* **Зачем `text`, а не `varchar(255)`?**
  * В PostgreSQL `text` и `varchar` внутри устроены одинаково (`varlena`) и работают с одинаковой скоростью. Лимит 255 — пережиток MySQL. Ограничения длины в Postgres задают через явный `CHECK`.

### 2. Ограничения и валидация
* **Зачем проверять в БД (`CHECK`), если в FastAPI уже есть Pydantic?**
  * Принцип **Defense-in-depth** (глубокоэшелонированная защита). Pydantic ловит ошибки только в HTTP-запросах. Но в базу могут писать сторонние скрипты, админы через консоль, миграции Alembic или фоновые воркеры. База — единственный абсолютный источник правды.
* **Почему приложение должно смотреть на код ошибки (SQLSTATE), а не на текст ошибки?**
  * Текст ошибки зависит от языка/локали сервера и версии PostgreSQL (в PG 18 код `RESTRICT` равен `23001`, а в PG 16/17 — `23503`). Код SQLSTATE и поле `CONSTRAINT NAME` стандартны и никогда не меняются.

---

### 3. Индексы и EXPLAIN
* **Почему PostgreSQL не создал индекс на внешний ключ `student_id` сам?**
  * Postgres автоматически создает индексы только для `PRIMARY KEY` и `UNIQUE`. Внешние ключи (`FOREIGN KEY`) автоматически не индексируются, их разработчик обязан создавать вручную.
* **Почему составной индекс `(course_id, student_id)` не помог поиску по `student_id`?**
  * B-tree индекс отсортирован по первому полю (`course_id`). Искать по второму полю без первого — это как искать в бумажном словаре слова по их последней букве (придется сканировать всю книгу).
* **Почему нельзя навесить индексы на все колонки подряд?**
  * Каждый индекс занимает 20–30% места от таблицы и замедляет все операции записи (`INSERT`, `UPDATE`, `DELETE`), так как при каждом изменении данных нужно перестраивать дерево индекса.

---

### 4. Запросы и транзакции
* **Почему в подсчете записей нужно писать `count(e.id)`, а не `count(*)`?**
  * `LEFT JOIN` для курсов без студентов оставляет строку с `NULL`. Функция `count(*)` считает количество строк (и выдаст ошибочную `1`), а `count(e.id)` считает только не-NULL значения (и правильно выдаст `0`).
* **Зачем нужна вторичная сортировка `ORDER BY likes DESC, id`?**
  * Чтобы пагинация была детерминированной. Если у двух курсов одинаковое число лайков, без `id` база вернет их в произвольном порядке, и при листании страниц один и тот же курс может появиться дважды или пропасть.
* **Почему лайк прибавляется в SQL (`likes = likes + 1`), а не в коде Питона?**
  * Защита от потери данных (Lost Update). Если два пользователя одновременно нажмут лайк, схема «прочитал в питон -> прибавил 1 -> записал» запишет 11 вместо 12. Команда `likes = likes + 1` блокирует строку на уровне БД (`FOR UPDATE`), выполняя операцию атомарно.
* **Почему параметризованный запрос (`$1`) защищает от SQL-инъекций?**
  * При обычной конкатенации строка `' OR '1'='1` меняет структуру SQL-команд (дерево разбора AST). В параметризованном запросе структура компилируется заранее, а параметр `$1` передается строго как текстовое значение (литерал), и база не может воспринять его как часть SQL-команды.

---

### 5. Обозначения в консоли `psql`
* `=>` — обычный режим ожидания команды.
* `->` — забыли точку с запятой `;` в конце команды, ввод продолжается.
* `=*>` — открыта незавершенная транзакция (`BEGIN`).
* `=!>` — внутри транзакции случилась ошибка; база будет игнорировать любые запросы, пока вы не напишете `ROLLBACK;`.

## ЧАСТЬ 3. Таблица сопоставления ошибок для API

| Нарушенное правило | SQLSTATE | Имя ограничения | Код ответа API | Почему такой код |
|---|---|---|---|---|
| Поле `title` пустое (`NULL`) | **23502** | `title` (column name) | **422** (или **500**) | 422 если ошибка клиента, 500 если баг в коде бэкенда |
| Кредиты = 0 (`credits <= 0`) | **23514** | `courses_credits_check` | **422** | Невалидное тело запроса |
| Отрицательные лайки | **23514** | `courses_likes_check` | **500** | Лайки меняет только сервер (`likes + 1`), минус — это баг бэкенда |
| Короткое имя студента | **23514** | `students_name_check` | **422** | Ошибка валидации данных пользователя |
| Повтор email студента | **23505** | `students_email_key` | **409 Conflict** | Конфликт уникальности |
| Повтор ID курса (первичный ключ) | **23505** | `courses_pkey` | **409 Conflict** | Курс с таким slug уже существует |
| Повторная запись на курс | **23505** | `enrollments_course_id_student_id_key` | **409 Conflict** | Студент уже записан |
| Запись на несуществующий курс | **23503** | `enrollments_course_id_fkey` | **404 Not Found** | Курс не найден |
| Запись несуществующего студента | **23503** | `enrollments_student_id_fkey` | **404 Not Found** | Студент не найден |
| Удаление курса с записями | **23503** / **23001** | `enrollments_course_id_fkey` | **409 Conflict** | Нельзя удалить родительский объект с активными связями |
